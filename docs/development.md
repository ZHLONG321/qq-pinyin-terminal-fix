# 开发说明

这份说明供阅读和修改源码时对照。正常使用按 [README](../README.md) 中的步骤操作即可。

## 输入法文件如何配合

Windows 通过 TSF 这套输入法接口通知 QQ 拼音处理输入。QQ 的接入文件是 `QQPinyinTSF.dll`，它再加载 `QQPinyin.ime`，由后者完成实际的输入处理。

这里的修复文件也叫 `QQPinyin.ime`。它收到 QQ 发来的函数调用后，修正候选框的显示设置，再把调用交给原来的输入法文件。因此源码里把它叫作“代理”。

修复时，原来的 `QQPinyin.ime` 改名为 `QQPinyinOriginal.dll`，留在原目录。原文件的内容和签名保留；本项目编译的代理没有签名。

`qq_proxy_setup.py` 从 QQ 的注册信息寻找这两个文件，核对文件后替换或恢复。它还会把原文件的访问权限复制给修复文件，让原来可以读取输入法的程序也能读取修复文件。

## 代理怎样修复候选框

QQ 拼音保存了 Terminal 传来的“控制台模式”标志，其中 `0x40` 这一位会使 QQ 屏蔽候选框通知。代理在 `WindowsTerminal.exe` 中找到当前线程的 QQ 输入法对象，清除这一位。

代理和手动修复工具共用 `src/qq_layout.cpp` 中的查找代码，不保存特定版本的函数地址、对象成员位置或接口表地址。查找分成几步：

1. 从文件中的 C++ 类型信息找到 `ITfTextInputProcessorEx` 接口，按接口定义找到输入法激活函数 `ActivateEx`。
2. 读取该函数的机器指令，跟踪第四个参数 `dwFlags` 被保存到对象的哪个位置。函数前部的寄存器复制、栈上暂存、对象指针调整都参与跟踪。
3. 按指令特征查找对 `0x40` 的判断，确认它们读取的成员位置与上一步一致。指令中的地址和位移由解码器读取，不作为固定字节匹配。
4. 从导入表找到 Windows 的 `TlsGetValue`，沿调用它的指令寻找线程索引。扫描从函数边界开始，逐条读取指令，避免把指令中间的字节误认成特征。
5. 实际修复时，用找到的线程索引读取对象，并核对同一类型的整组接口表。只有对象和标志位置都能唯一确定时，才清除 `0x40`。

因此，函数和接口表换了地址、对象成员前面增加了字段时，查找代码可以重新读出位置。查找依赖微软 x64 C++ 类型信息、激活参数的保存方式和 TLS 调用形式；如果新版删除类型信息或改写了这些逻辑，代理会跳过修复，照常转发原来的输入功能。

指令解析使用 `third_party/hde64/` 中的 HDE64，来源和许可证见该目录说明。`build.py` 同时编译代理和 `dist/x64/qq_layout.exe`。后者供 Python 手动修复工具调用，只读取目标文件，不加载或执行 QQ 的代码。Python 工具在修改内存前，还会核对本次找到的指令与正在运行的模块一致，避免把更新后的磁盘文件位置用于旧进程。

修复脚本通过代理中保留的一段固定提示文字识别本工具的文件，因此重新编译后仍可恢复先前放入的代理。复制文件后比较的校验值只用来确认副本与本次原文件一致，不限定 QQ 拼音版本。

代理保留原文件全部 18 个导出函数的名称和序号。这些是 QQ 的接入文件用来寻找输入功能的入口。代理转发这些调用，原文件加载后保留到程序退出。

原文件通过同目录下的完整路径加载。初始化在第一次调用输入法函数时发生；Windows 通知 DLL 加载的回调只记录自身位置。

## 对照源码的位置

以下位置来自测试过的 QQ 拼音 6.6.6304.400，仅供对照分析。自动查找代码不使用这些地址。分析时的 `QQPinyinTSF.dll` 的 SHA-256 为 `eb0b1a0da279ac841f3de733afc35ab3132b1d6c7394a1c815e1a2849c38044b`，这是根据整个文件内容算出的校验值。

表中的位置是从这个模块的加载地址算起的相对位置，反编译工具通常把它叫作 RVA。

| 相对位置 | 作用 |
| --- | --- |
| `0x97d0` | 把 Windows 传入的输入法激活标志保存到 QQ 对象中，存放位置距对象起点 15260 字节 |
| `0xaf70` | 保存的标志含 `0x40` 时，拦截候选框变化、关闭和打开通知 |
| `0x8550` | 把没有被拦截的通知传给 QQ 候选窗口 |
| `0xa230`、`0xa400` | 保存的同一标志也会使 QQ 在窗口激活时隐藏输入法界面 |
| `0x2a33c` | 保存 QQ 寻找当前线程输入法对象时使用的 TLS 索引；TLS 是每个线程各自存放数据的地方 |

Terminal 在[对应版本的源码](https://github.com/microsoft/terminal/blob/v1.24.12741.0/src/tsf/Implementation.cpp)中使用控制台模式激活 TSF。表中的 QQ 行为来自组件分析和运行时读取。

自动查找代码在这个 QQ 文件上找到了与先前分析一致的线程索引、成员位置和接口表，代理及查找工具均编译通过。候选框、翻页和选字的实际使用测试来自先前的固定位置代理；自动查找版需要重新执行修复并重开 Terminal 后试用。

## 手动排查正在运行的 Terminal

`qq_terminal_fix.py` 保留了最初的内存修复方式。它读取或修改已经运行的 Terminal，不替换磁盘上的输入法文件。

先按 README 运行 `uv run build.py`，生成它需要的自动查找工具。

先在任务管理器的“详细信息”页找到目标 `WindowsTerminal.exe`，记下 PID 列的数字。PID 就是 Windows 给运行中的程序分配的编号。

把下面的 `12345` 换成这个编号。第一条查看当前状态，第二条尝试修复当前窗口：

```cmd
uv run qq_terminal_fix.py status --pid 12345
uv run qq_terminal_fix.py apply --pid 12345
```

工具会保存原来的值，并打印对应的恢复命令。恢复记录在项目的 `tmp` 下。

同一个 Terminal 进程可能有多个窗口线程。如果工具无法确定要改哪个线程，会要求通过 `--tid` 指定线程编号，需要结合调试记录选择。

这种修改作用于当前的输入法对象。重新打开 Terminal 或重新启用输入法后，可能需要再次执行；想让新开的 Terminal 自动修复，使用 README 中的 `fix.py`。
